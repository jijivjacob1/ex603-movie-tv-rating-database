1. Modelling Justification
Every table in this schema uses a surrogate primary key — an auto-incrementing integer such as movie_id, user_id, or rating_id — rather than a natural key drawn from the data itself. Titles aren't unique (multiple films share a name, remakes exist), and usernames or emails or display names can change over time. A surrogate key stays stable for the life of the row regardless of what happens to descriptive columns, which matters because movie_id and user_id are referenced throughout the schema as foreign keys. If a natural key were used and later needed to change, that change would cascade through every referencing table. Surrogate keys also keep joins cheap, since integer comparisons are faster than comparing variable-length strings across large rating tables.

ON DELETE behavior was chosen per relationship based on what a deletion should actually mean. Movies are never hard-deleted; instead, an is_available flag marks a title as retired from the catalog while preserving the row and all ratings tied to it, since historical ratings retain value even for titles no longer offered. For the foreign key from ratings to movies, this makes ON DELETE RESTRICT the right choice — the application should never be able to physically remove a movie that still has ratings attached, forcing any true deletion through the soft-delete path instead. The relationship between ratings and users is handled differently: when a user account is deleted, ON DELETE CASCADE removes that user's ratings along with them, since a rating with no rater isn't a meaningful record, and most privacy-driven account deletions expect associated activity to go too. 

Several rules were pushed down into the schema itself rather than left to application code, because they're cheap for the database to guarantee and expensive to guarantee correctly at the application layer under concurrent access. A UNIQUE constraint on (user_id, movie_id) in the ratings table prevents a user from rating the same title twice, closing a race condition that application-level "check then insert" logic can't fully close on its own. NOT NULL constraints on movie_id and user_id in ratings enforce that a rating always refers to a real user and a real title, since a rating missing either value is meaningless. 

2. Reflection

One decision the requirements left open was whether a user can submit only one rating per movie, or whether re-rating over time should be preserved as history. I chose to enforce a single current rating per (user_id, movie_id) pair via a unique constraint, with a new rating simply overwriting the old one, rather than storing every rating a user has ever given a title as a separate timestamped row. A different designer could reasonably choose the history-preserving model — it captures how opinions change after a rewatch and supports "ratings over time" analytics.

I defend the single-current-rating approach based on the platform's expected read and write patterns. Reads dominate by a wide margin: every movie page, recommendation, and "top rated" list needs a fast average score computed from the ratings table. Keeping exactly one row per user per movie keeps that aggregation cheap and unambiguous, with no need to filter down to "most recent" rating per user before averaging. Writes, by contrast, are infrequent and tolerant of being treated as upserts — a user re-rating a movie is rare compared to how often that movie's average gets read, so collapsing it into a single UPDATE is a reasonable trade. If usage data later showed rating-history features were worth the extra cost, that could be layered in as an optional ratings_history table without disturbing the core schema the read paths depend on.
